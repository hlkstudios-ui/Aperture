# Architecture

## Current State

The repository was audited on 2026-08-15. It is greenfield: the only initial files were `Command%20A(1).md` and `Command%20B(1).md`. There was no application code, source directory, package manifest, database schema, migration history, infrastructure configuration, test suite, CI configuration, or Git metadata.

Phase 1 now provides a Next.js web shell, FastAPI service, PostgreSQL migration baseline, Redis connection, and MinIO development bucket. PostgreSQL runs as a Homebrew service on this workstation; Redis and MinIO run as local development processes because the pre-existing Homebrew Redis configuration referenced unavailable modules.

Phase 2 authentication uses distinct customer and administrator tables and cookie names. Browser tokens are high-entropy opaque values; only SHA-256 token digests are stored in PostgreSQL. Passwords use Argon2id. Customer and administrator session lifetimes, revocation, device metadata, Redis-backed login throttling, trusted-origin checks, and admin audit events are enforced by the API. Next.js Proxy performs an optimistic Studio-cookie redirect, while the dynamic Studio page performs a secure API/database-backed authorization check before rendering.

Password recovery uses expiring one-use opaque tokens whose digests alone are persisted. A successful reset changes the Argon2id password hash and revokes every customer session. Development and tests expose the reset token only to support local acceptance testing; staging and production require configured SMTP delivery. Administrator MFA secrets are encrypted at rest, TOTP confirmation is required before activation, and recovery codes are independently hashed and consumed once.

Phase 3 adds a normalized catalog around separate Movie and Series aggregates. Series own ordered Seasons, which own ordered Episodes; Edition, Credit, Artwork, and Trailer/Clip records enforce exactly one valid title parent at the database layer. Shared Genre, Theme, Tag, Person, Character, Company, Franchise, Language, and Country records use foreign-key or association-table relationships rather than copied strings. Draft/ready/published/archived lifecycle state controls customer visibility, while authenticated administrator APIs retain full lifecycle access and write audit events.

Catalog request contracts validate slugs, lengths, runtimes, parent cardinality, and reference identifiers before persistence. PostgreSQL constraints remain the final integrity boundary. Customer reads load published Movie/Series aggregates and explicitly exclude unpublished Episodes. Development seed data is original, idempotent, and environment-guarded; it is test content rather than production catalog completion.

Phase 4 consumes those public APIs from Next.js Server Components using uncached server-side fetches, so customer HTML reflects the current published catalog without exposing internal administrator data. Dynamic slug routes convert API 404s into route-level not-found UI; unexpected failures reach a recoverable error boundary; a root loading boundary provides meaningful skeletons during navigation. The small season browser is a Client Component because selection is interactive, while title and hierarchy retrieval remain on the server. Playback, My List, and progress controls expose unavailable states instead of inventing media or user signals before their domain phases.

Phase 5 layers the operational Studio onto the same catalog boundary. Server-rendered Studio pages authorize the administrator before fetching draft-capable data; Client Components are limited to interactive forms whose Server Actions reauthorize, call the protected API with the opaque administrator session, and revalidate affected routes. Draft preview routes remain inside the protected Studio tree, while public catalog endpoints continue to return only published records. Movie and series workflows share the normalized Phase 3 models, and episode batch input is translated into ordered API writes rather than a parallel persistence path.

Phase 6 introduces MediaAsset as the durable upload control record. Small sources use one short-lived signed PUT; sources above 16 MiB use a persisted private multipart session with individually signed parts. Resume state and completion ETags come from object storage rather than the browser, part numbers are range-checked, and cancellation aborts the remote session. Reselecting the same filename/size/SHA-256 resumes missing parts after interruption. Browser hashing is incremental, and both strategies converge on object length, checksum metadata, a full streamed SHA-256, and container-signature verification before completion.

Upload integrity completion now enters a persisted malware quarantine before `AssetState.completed`. Development/staging use a deterministic EICAR marker scanner for repeatable acceptance; production settings require a private ClamAV-compatible INSTREAM endpoint. The scanner streams the already-private object without creating a public URL. Clean verdicts record engine/time and permit processing; detected signatures fail the asset; connection, timeout, or malformed-verdict failures remain non-processable and retryable. Production preflight sends only clamd PING, never media. The processing API continues to accept only completed assets, making a clean verdict an enforced prerequisite rather than a UI convention.

Phase 7 uses PostgreSQL as the authoritative processing state and Redis as queue transport. The API creates one processing job per completed asset and enqueues only its opaque UUID. Workers claim with a PostgreSQL row lock and expiring UUID ownership lease, renew the lease during long-running FFmpeg work, and condition every progress/terminal write on that owner. Duplicate deliveries cannot claim concurrently; expired work is boundedly requeued, and repeated crashes become a terminal failure after the configured attempt limit. Each attempt clears the job-specific processed prefix before source-aware H.264/AAC transcoding, derived images, subtitle extraction, and final HLS validation. Only validated outputs are copied to stable private keys and marked Ready.

Scene enrichment uses the same PostgreSQL-authoritative pattern: row-locked claims, expiring UUID ownership, background renewal, guarded progress and terminal writes, and bounded expired-job recovery. Before replacing transcript/search projections, the worker locks and revalidates its ownership in the same transaction, preventing a recovered stale worker from committing derived scene data. Repeated lease loss ends in an explicit terminal stage rather than an infinite retry loop.

Phase 8 adds PlaybackSource as the deliberate boundary between catalog identity and immutable Ready processing output. A source targets exactly one movie or episode and carries editorial skip markers; database constraints prevent ambiguous title/job assignments. Playback configuration requires a customer session and active profile, and public titles must be published. Media requests use opaque source-relative URLs through the authenticated API, which resolves allowlisted persisted output keys server-side and supports byte ranges without disclosing MinIO credentials or filesystem/object paths. Production deployment can replace this proxy with short-lived CDN authorization while retaining the same access decision.

Production CDN mode issues a five-minute path grant bound to playback source and active device session. Before issuing it, the API atomically acquires an expiring Redis lease against the account's active `simultaneous_streams` entitlement (one stream when no valid entitlement exists); repeat requests from the same device refresh rather than consume another slot. API-proxy media and secret-origin misses refresh an existing lease but cannot create one, Redis failure denies playback, and abandoned slots expire after the configured bounded window. The edge verifies its HMAC and expiry before cache lookup; its cache key removes the grant but retains the immutable source/object identity. Cache misses reach a separate secret API origin which verifies the same grant, active session, current title/edition rights, Ready-source prefix, traversal-safe object path, and lease before reading private Spaces. Full immutable objects may cache; byte ranges bypass insertion and preserve 206 semantics. Development and staging retain the cookie-authenticated proxy.

The watch surface is a Client Component around HLS.js, with native HLS fallback where available. It requests protected HLS resources with customer credentials, exposes adaptive and pinned quality modes, tracks/audio/subtitles, core accessible controls, skip markers, next-episode navigation, and browser media integrations. WatchProgress is unique per active profile and playback source. The API validates finite positions and duration tolerance, clamps bounds, and derives percentage/completion; the browser throttles saves and persists on pause and page exit before restoring progress on the next visit.

Phase 9 separates editable homepage state from live delivery. HomepageConfiguration owns the draft hero and ordered relational HomepageRails/HomepageItems. Publishing serializes the complete draft into one immutable snapshot in the same transaction as the publication timestamp; customer requests never assemble a hybrid of old and partially edited records. Public resolution expands pinned and dynamic sources, de-duplicates titles, enforces title lifecycle and rights availability, and applies rail start/end instants. Studio preview resolves the current relational draft without weakening the public boundary.

Movie and Series now carry timezone-aware publish, unpublish, rights-start, and rights-end instants. Pydantic rejects offset-free timestamps, PostgreSQL stores `timestamptz` and enforces ordered windows, and application comparisons use UTC-aware instants. Due publication state is materialized transactionally on public catalog/homepage access, while rights windows remain an independent availability condition. Deployment still needs an always-on scheduler if state transitions must materialize in the absence of request traffic.

Phase 10 separates commercial truth into Plan, Subscription, PaymentReference, and Entitlement records. Subscription state is never inferred from a checkout request: only a provider integration/webhook may materialize provider references, payment state, and granted entitlements. The BillingProvider protocol isolates that future adapter. The local development implementation advertises itself as non-production and always refuses checkout, so demos cannot accidentally present an unpaid account as subscribed. Staging and production configuration reject the development stub.

The account boundary is customer-authenticated and ownership-scoped. It returns only the caller's subscription, active entitlement windows, profiles, and unrevoked/unexpired sessions. Individual device revocation verifies ownership; password changes require the current Argon2id credential and revoke all other sessions while retaining the initiating session. Browser cookies remain opaque and hashed in PostgreSQL, and no payment credential or provider secret is exposed to the account UI.

Phase 11 stores customer analytics as typed, profile/session-owned raw events and independently queryable day/title aggregates. Client UUIDs make ordinary events idempotent; progress uses a profile/title/30-second bucket so retries and frequent saves cannot create unbounded writes. Redis limits are weighted by batch size, request batches and JSON properties are capped, event time is UTC-bounded, and only an explicit non-PII property allowlist is accepted. Identified bots and internal events remain distinguishable in raw storage and are excluded from customer aggregates.

Phase 12 computes recommendations on demand with a named, deterministic `rules_v1` strategy. Candidate eligibility reuses the public catalog's publish schedule and rights-window boundary. Ranking combines immutable published-homepage editorial membership, taxonomy overlap with the active profile's watched titles, validated profile genre choices, and recent non-bot aggregate plays. Any saved movie progress excludes that movie, and episode progress excludes its owning series. Stable score/date/title/ID ordering prevents accidental ranking churn, while every response exposes reason codes and cold-start/exclusion state. This is deliberately an explainable rule system, not a machine-learning model; cached candidates and offline weight evaluation are later scaling work.

Phase 13 keeps Taste DNA as a derived, non-authoritative projection over profile-scoped `WatchProgress`, `PlaybackSource`, and normalized catalog metadata. Completion percentage weights observed titles, while response counts and confidence make evidence coverage inspectable; no inferred preference is persisted as behavioral fact. Movie Prescription reuses public scheduling/rights eligibility, applies requested time/genre/language/era/watch-state/unwanted constraints before scoring, and maps mood/pacing/intensity only through controlled theme/tag terms. Each output dimension distinguishes matched, neutral (not requested), and unavailable (requested but unsupported) states. `prescription_rules_v1` is deterministic and explanation text is assembled from the same evidence that contributes points.

Privacy controls distinguish required product state from optional measurement. Watch progress remains profile-owned because it powers resume plus deletion/export workflows; optional analytics default off and ingestion checks persisted consent. Withdrawal atomically timestamps the choice and removes retained raw events for that profile, while already-produced aggregate rows contain no profile identifier. `no_algorithm` also makes Discover skip watch progress and explicit profile affinities, using only editorial programming and anonymous aggregate popularity with an explicit strategy disclosure. Taste DNA and Movie Prescription remain deliberate private tools invoked by the customer rather than ambient ranking.

Phase 14 separates mutable resume state (`WatchProgress`) from durable personal history (`ViewingActivity`). A profile/source activity number is unique; completion is a state transition, and a new rewatch cycle begins only when a previously completed source restarts near the beginning. Client watch deltas are bounded to 60 seconds per save and total observed seconds are capped at source duration per cycle. The lifetime/year Passport joins activities through playback sources to normalized movie, episode/series, taxonomy, and credit data. All aggregates are computed inside the authenticated active-profile boundary, reports declare their `viewing_activities` provenance, and public sharing stays disabled until privacy controls exist.

Phase 15 establishes scene intelligence as versioned evidence attached to immutable Ready playback, not as generated customer-facing prose. Each structured fact retains a version-local provenance source and license basis; timed facts carry database-enforced ranges, while confidence and manual-verification fields preserve epistemic state. Draft/review versions are editable, validated/published versions are immutable, and publication atomically replaces the title's prior published version. Structural validation checks source ownership, playback bounds, ordinal continuity, and temporal overlap before validation. Enrichment jobs currently provide durable queue/state coordination only: subtitle/transcript ingestion, segmentation, conservative entity linking, and search indexing are intentionally deferred to Phase 16, and no chatbot reads this data.

Phase 16 activates the enrichment queue with a separate Redis-backed worker. It resolves only processed subtitle objects whose exact internal URI is declared by a version-local subtitle/transcript provenance record with an administrator-supplied license basis. WebVTT payloads are size-bounded, UTF-8 decoded, timestamp-validated, and either aligned to existing editorial scenes or grouped by conservative silence/maximum-duration boundaries. Cue text, derived scene summaries, confidence, and verification state remain inspectable; no named character, relationship, craft, or production fact is inferred. Search uses generated PostgreSQL `tsvector` documents and a GIN index, so embeddings are unnecessary for the current corpus. The index remains administrator-only until Phase 17 supplies fail-closed spoiler filtering for every retrieval path.

Phase 17 centralizes customer scene retrieval behind a profile-authenticated spoiler policy rather than allowing feature-specific queries over raw tables. Protected retrieval uses an inclusive `reveal <= playback timestamp` cutoff; scene and transcript text reveal at their end time, while a relationship reveals only after itself and both entities are known. Full mode substitutes source duration for the cutoff only after the same profile has a completed durable viewing activity for that source, so another profile's completion cannot unlock spoilers. The service validates version provenance, scene ownership, finite numeric values, source duration, relationship locality, and payload safety on every response. Invalid facts are omitted and surfaced only as counts/state, never partially serialized. SceneLens and later Ask This Movie must consume this service instead of querying intelligence tables directly.

Phase 18 makes SceneLens the first consumer of that centralized policy. The player sends its current timestamp to the context endpoint only when the viewer opens the overlay; no raw intelligence table is exposed to the browser. The context service resolves normalized Character/Credit/Person identity and prior appearances inside the same cutoff, while missing actor or craft evidence remains an explicit empty state. The desktop overlay occupies a bounded side region and the mobile overlay a scrollable bottom sheet; pausing offers entry without automatically covering the movie. SceneBookmark and SceneNote are active-profile/source-owned records with optional validated scene links and timestamp bounds. They store text and navigation positions only—never captured frames, manifests, or media bytes.

Phase 19 keeps Q&A downstream of the same spoiler service. `structured_templates_v1` first classifies a bounded intent and then formats only typed allowed facts; it does not query raw transcripts, extrapolate causality, or invoke an unconfigured language model. A question unsupported by the current allowed facts returns a stable unavailable statement plus uncertainty instead of a plausible guess. Customer responses expose evidence kinds and reveal times but not internal IDs or provenance URIs. Internal AskMovieLog records retain the published version and exact used fact identifiers while hashing and discarding raw question text. This produces auditable grounding without building a sensitive conversational transcript; future model-backed expansion must preserve this retrieval and logging boundary.

Phase 20 adds two purpose-built moment queries downstream of that same protected context. Who Was That filters current-scene character, entity, and relationship facts again at the effective cutoff before formatting identity, actor, prior-appearance, and known-relationship fields. What Did I Miss validates a past-only interval and selects only scene-summary facts whose completion reveals fall within it; it neither summarizes raw transcript spans nor includes a partially watched scene. This double filtering keeps endpoint behavior fail-closed even if an upstream context object is accidentally over-inclusive, while explicit unavailable states prevent plausible fabrication.

Phase 21 projects the protected fact set into a graph rather than querying scene tables independently. Entity records map to stable canonical keys so repeated appearances can converge, while an edge is emitted only when the relationship and both referenced entities survived the spoiler boundary. Current-character emphasis derives from already-allowed current-scene character facts. The visual SVG is progressive enhancement over a semantic relationship list with endpoint labels and reveal timestamps; zoom changes canvas scale and the bounded viewport provides keyboard-scrollable pan without making the graph the sole accessible representation.

Phase 22 begins as an aggregate over shared domains rather than a family of isolated feature tables. Artwork now carries the minimum permission and spoiler metadata needed for a private still gallery; permitted records must be stills attached to an approved scene, have a timestamp and rights basis, and are deleted with that scene. The Cinephile service reuses the published spoiler context for still/music/filmmaking visibility, normalized catalog credits and editions for non-plot exploration, and the profile viewing ledger for rewatch facts. Still bytes remain in private object storage and are delivered only after source authorization plus membership in the caller's current allowed gallery; responses expose an authorized URL and accessibility metadata, never raw object keys or internal legal text.

Edition Vault extends the existing Edition aggregate rather than treating cuts as labels on one stream. A PlaybackSource may point to one edition, and its distinct ProcessingJob supplies that cut's actual renditions, audio, and subtitles; partial unique indexes preserve one legacy unversioned source while permitting one source per edition. Edition metadata records rights and intended presentation separately from processed technical tracks. Verified difference records relate two same-title editions and retain an internal source note; customer comparison text is withheld until the active profile has a completed activity for any source of that title. Playback chooses an in-rights default edition deterministically, maintains contain-fit presentation, and asks HLS to prefer the edition/title original-language track when available.

The initial film knowledge graph is a read projection over normalized catalog truth, not a second unsynchronized graph store. Nodes and labeled edges are derived from a visible movie's taxonomies, locales, franchise, Credit/Person/Company/Character records, and other currently available titles connected through those verified records. Customer links point to real discovery destinations, while a parallel semantic edge list makes the relationship structure usable without the visual card layout. Person/company destinations apply the same publication and rights predicates to their filmographies. Relationships that the existing domain cannot prove—such as influence, source material, remake, or explicit sequel direction—remain absent until a sourced relationship model is added.

The completed toolkit adds sourced directed title relationships as explicit administrator-verified facts rather than deriving sequel, remake, adaptation, source-material, influence, or companion meaning from similarity. Collections, private user lists, and chaptered Film Journeys share ordered curation primitives while retaining editorial versus profile ownership boundaries. Journey completion is independently profile-owned. The After-Credits Room is derived only after durable completion and only from recognized, published provenance-backed categories. My List is the customer shortcut over the private-list aggregate, not a parallel watchlist table. Rewatch intelligence remains opt-in and activates only on a genuine later viewing cycle; saved scenes and notes stay private to the active profile. Studio still creation selects a worker-derived protected asset in the context of a published scene and records the permission, reveal, accessibility, and rights evidence needed by the existing private-delivery boundary.

Phase 23 stores homepage strategy on `ProfilePreference`, so profiles sharing an account or device do not silently share a ranking choice. Curated mode remains the immutable published editorial snapshot. No-Algorithm Mode is the separately named `deterministic_catalog_indexes_v1` read projection over the same publication and rights predicates: created time, normalized title, release year, verified director credits, country, genre, and published collection order are its only inputs. Stable tie-breakers and UUIDv5 rail identities make repeated responses reproducible. The renderer deliberately does not read watch history, recommendations, popularity, Taste DNA, analytics, or randomness; the API exposes the strategy name so the customer surface can state that boundary accurately.

Phase 24 separates profile-owned drafts from publicly readable community projections. Numeric ratings may aggregate immediately, while review text and public/unlisted user lists begin pending and require an administrator decision after every content edit. Public queries select only approved current records, then apply viewer-specific block and mute filtering; activity entries are references rather than copied payloads, so later rejection, removal, or privacy changes suppress stale activity automatically. Follows are directional, blocks are enforced bidirectionally and remove existing follows, and mutes affect only the acting profile's reads. Reports accept exactly one approved public target and are de-duplicated per reporter/target. Redis limits every customer mutation family. Administrator decisions require reasons and produce both the general audit record and a durable moderation-action ledger; target foreign keys may become null on account deletion so the non-identifying decision history survives without preventing erasure.

Phase 25 treats a movie club as a private membership boundary and a watch party as synchronization metadata, never as media authorization. Club invite and room credentials are stored only as hashes and establish membership/presence, while every participant independently traverses the ordinary session, active-profile, publication, UTC rights-window, edition-rights, and Ready-source checks on every state read or mutation. Territory enforcement is a later hardening increment and is not attributed to Phase 25. Host commands use monotonic optimistic revisions; clients reconcile revision or position drift against server time. Ending a party closes admission, completes the assigned schedule and joined-member history, and allows orderly departure. Discussion inherits profile block/mute filtering, ownership removal, moderator roles, and Redis limits from the broader safety model.

Phase 26 stores internationalization and caption behavior at the profile boundary so accounts with different viewers do not share language, timezone, audio, or accessibility choices. IANA timezone validation happens at input; catalog/media language matching accepts common ISO 639 two/three-letter aliases without rewriting source metadata. A same-origin document-locale projection applies the active profile's semantic language and RTL direction while anonymous and administrator-only sessions remain quiet defaults. The primary subtitle remains a standard browser text track and the optional second licensed track is additive; caption size, background, and position are presentation preferences, not transformed subtitle content. Modal player tools share one keyboard focus contract. Automated axe checks supplement—not replace—real keyboard, responsive, two-track media, and visual acceptance.

Raw events retain user/profile foreign keys and therefore disappear with account/session deletion; aggregated rows contain only day, type, title dimensions, counts, and sums. Ingestion performs bounded expired-row cleanup using the configured retention window. The current synchronous recomputation provides immediate, deterministic development observability; production scale will move ingestion and reconciliation to partitioned queue consumers without changing the public event contract.

## Platform and tenant boundary

The commercial target adds a marketplace control plane above the current application while keeping
each renter in an isolated Aperture cell built from the same canonical immutable release. Platform
identity, template rentals, and future platform billing remain separate from cell viewers, Studio,
data, and tenant commerce. The current repository is still one owner-controlled cell; it does not
implement shared-database tenancy, cross-cell provisioning, or cross-cell hostname routing. See the
[platform control-plane contract](PLATFORM_CONTROL_PLANE.md) for the authoritative foundation and
delivery tranches, and [tenant monetization architecture](TENANT_MONETIZATION.md) for cell isolation
and the separate tenant-commerce boundary.

The disabled-by-default transitional platform slice requires verified mailbox ownership before any
rental write. Authenticated confirmation and password-rotating email-link recovery share a one-use,
delivery-safe token lifecycle; recovery revokes every pre-existing platform session. Unpaid
reservations are quota-bound and expire to immutable history, releasing their slug and owner
membership atomically. These controls prevent disposable accounts from holding hostnames forever;
they still do not constitute payment, provisioning, a routable tenant, or a production platform
launch.

## Target Topology

The initial architecture follows the greenfield preference in Command B:

- Customer and Studio web application: TypeScript, React, and Next.js.
- API: Python and FastAPI with typed Pydantic contracts.
- Persistence: PostgreSQL with SQLAlchemy and Alembic migrations.
- Cache and job coordination: Redis.
- Media storage: S3-compatible object storage (MinIO locally).
- Background work: Python workers with idempotent jobs and explicit failure states.
- Media processing: FFmpeg and ffprobe producing HLS renditions and derived assets.
- Browser testing: Playwright; frontend unit tests and pytest for backend services.

The customer experience and private single-administrator Studio share domain APIs while retaining explicit authorization boundaries. Advanced scene intelligence will be built only after catalog, authentication, media, player, progress, and spoiler-boundary foundations exist.

## Initial Boundaries

- `apps/web`: customer UI and `/studio` Admin Studio.
- `apps/api`: HTTP API and domain services.
- `workers/media`: upload validation and media processing.
- `packages`: shared contracts or configuration only when reuse justifies them.
- `infra`: local stateful-service orchestration and deployment assets.
- `docs`: architecture, development, decisions, status, and operations.

These paths are target boundaries for Phase 1 and may be refined before code is generated if dependency compatibility requires it.
